# Phase 3 plan: Swift + Metal PIV library and Mac app

## 1. Context

The Rust tool (`piv` CLI: info / analyze / smooth) works well but every change means a CLI
run and a video to open. Phase 3 adds a native path for faster iteration:

1. **Repository split.** Move the Cargo workspace into `rust/`, so `rust/` and `swift/` can
   be built, tested and versioned separately.
2. **`PIVKit`**, a Swift package that does the same per-pair analysis as `piv-core` with the
   heavy work (preprocessing, FFT cross-correlation, peak finding) in Metal compute kernels.
3. **`PIV.app`**, a SwiftUI Mac app built on `PIVKit`: import a clip, set capture frame rate,
   FOV, camera-to-sheet distance and the analysis parameters, run the analysis off the main
   thread with a progress indicator, then play the quiver result.

The Rust code stays the reference implementation. The Swift port is judged by how closely it
matches Rust on the same input (§6), not only by synthetic tests.

## 3. PIVKit: what gets ported

| Rust (`piv-core` / `piv-io`) | PIVKit | Where it runs |
|---|---|---|
| `frame::FrameRate` (rational, NTSC snapping, parsing) | `FrameRate` | CPU |
| `grid::Grid` | `Grid` (same centring and `center_x/y`) | CPU |
| `preprocess`: background min/mean, Gaussian blur, local normalize | `Preprocessor` | **Metal** |
| Window signal mask (integral-image mean/std) | Computed in the correlation kernel from the raw window | **Metal** |
| `correlate`: window load (bilinear), mean removal, FFT correlation, `find_peak` (Gaussian 3-point fit, PPR with footprint exclusion) | `Correlator` | **Metal** |
| `multipass`: predictor sampling, symmetric window placement, passes | `PIVAnalyzer` | CPU orchestration + Metal per pass |
| `validate`: PPR, out-of-range, normalized median, replacement | `Validator` | CPU (≈2 k vectors per pass; not worth a kernel) |
| `flowstats` (vorticity, KE, coverage, noise floor) | `FlowStats` | CPU |
| `smooth::temporal` (mean/median, min-support) | `TemporalSmoother` | CPU (D5) |
| `scale::ScaleSpec` (px/mm or pinhole FOV + distance) | `ScaleSpec` | CPU |
| `metadata`: Sony `NonRealTimeMeta` capture rate | `CaptureRateProbe` (ISO-BMFF box scan, port of the Rust probe) | CPU |
| `decode` (ffmpeg subprocess) | `FrameReader` on **AVFoundation** (no ffmpeg dependency) | VideoToolbox |
| `render` quiver + `encode_video` | `QuiverRenderer` (Metal) + `AVAssetWriter` | **Metal** / VideoToolbox |
| `overlay` (readout, chart burned into PNGs) | Live SwiftUI overlays in the app (D4) | — |
| HDF5/NPZ writers, `smooth --sweep` CV | Not in phase 3 (§9) | — |

### 3.1 Decoding (AVFoundation)

- `AVAssetReader` with `AVAssetReaderTrackOutput` asking for
  `kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange` (the 10-bit variant for >8-bit sources). The
  Y plane is the luma we analyse, so there's no RGB conversion, the same as Rust's `gray`.
- **Range parity:** ffmpeg's `gray` output expands video-range luma (16–235) to full range.
  The upload kernel does the same, (Y − 16) / 219 clamped to 0–1, so intensity thresholds like
  `--min-mean 0.04` mean the same thing in both ports. Full-range sources are passed through
  unchanged. `--channel green` maps to requesting BGRA and taking G.
- Planes come in as `CVPixelBuffer`s and go to Metal through `CVMetalTextureCache` without a
  copy. The upload kernel crops the ROI and writes a dense `float` buffer, the same layout as
  Rust's `Frame`.
- Frame indexing: a start time is converted to a frame index with the container rate, as in
  Rust. Frames are counted from the reader start and checked against presentation timestamps.
  The 40 background samples spread across the clip use one short `timeRange` read each.
- All five sample clips are 8-bit H.264 4:2:0 (checked with ffprobe), which AVFoundation
  decodes in hardware.

### 3.2 Correlation on the GPU

A pass correlates every window of the grid at once (1080p at 64 px / 50 %: 59 × 32 = 1 888
windows; at 96 px, 819).

1. **Load kernel** (one threadgroup per window): place windows A and B at their fractional
   origins (the `place` logic from `multipass.rs` runs on CPU and is passed in a buffer of
   origins). Sample with manual bilinear interpolation in `float`, not the texture sampler,
   whose 8-bit fractional weights would bias sub-pixel results. Reduce in threadgroup memory:
   the window mean (subtracted), the energy Σv², and the raw-intensity mean/std at the rounded
   origin for the signal mask.
2. **FFT.** Window sizes aren't powers of two (the default is 96 = 3 · 2⁵). A whole
   96 × 96 complex plane (72 KB) doesn't fit in 32 KB of threadgroup memory, so the 2-D FFT is
   split into **batched 1-D FFTs**: one kernel transforms all rows of all windows, the next all
   columns. Each 1-D transform (≤ 128 points, < 1 KB) runs in threadgroup memory with radix-2
   and radix-3 stages, so any `n = 2ᵃ·3ᵇ` works. The two real windows are packed as one complex
   input (A + iB) and separated after the forward transform, which halves the work. Then
   conj(A)·B, inverse FFT, and scaling by 1/(n²·√(Ea·Eb)), as in Rust.
3. **Peak kernel** (one threadgroup per window): arg-max, half-width search, the
   local-maximum scan outside the excluded footprint (for PPR), the 3-point Gaussian or
   parabolic fit, and wrap-around. Output per window: `dx, dy, ppr, flag`.

Window sizes the FFT can't handle (e.g. 80 = 2⁴·5) are rejected in config validation with a
clear message. Supporting radix 5 later is cheap if needed.

**Alternative considered:** `MPSGraph`'s FFT ops. They are less code, but they work through
graph tensors (an extra copy per pass), and their support for non-power-of-two sizes and their
batching cost need measuring. Milestone 3 starts with a short spike: MPSGraph FFT vs the
custom kernel on 819 × 96² and 1 888 × 64² batches. If MPSGraph is within ~20 %, we use it and
keep the custom kernel out. I'll report the timings.

### 3.3 Pipeline and concurrency

```
FrameReader (AsyncSequence of CVPixelBuffer, own task)
  → upload + preprocess (Metal)  → PreparedFrame ring (stride + 1 GPU buffers, recycled)
  → per pair: for each pass { CPU place origins → GPU load/FFT/peak → CPU validate }
  → PairResult (VectorField + summary + FlowStats)
  → QuiverRenderer → AVAssetWriter
```

- `PIVSession` is an **actor** that owns the Metal device, pipelines and buffer pools. The
  public API is `func analyze(_ request: AnalysisRequest) -> AsyncThrowingStream<AnalysisEvent, Error>`.
  Events are `.progress(pairsDone, pairsTotal, stage)`, `.pair(PairResult)` and
  `.finished(RunResult)`. Cancelling the consuming task stops decoding and GPU submission.
- Two or three pairs are in flight at a time (command-buffer completion handlers resume
  continuations), so CPU validation for pair *k* overlaps GPU correlation of pair *k + 1*.
- Swift 6 language mode with strict concurrency. Metal objects stay inside the actor, and only
  `Sendable` value types (fields as `[Float]` plus `Grid`) cross out of it.
- The background estimate (min of N frames across the clip) is a first stage with its own
  progress.

### 3.4 Quiver video

- `QuiverRenderer` draws on the GPU: the background frame with the same auto gain as
  `QuiverStyle::auto` (99th percentile from a sparse sample), then instanced arrows (shaft +
  head, antialiased) coloured by magnitude with the same colour map and magenta for replaced
  vectors. Arrow scale and colour range are fixed from the first pairs, the same as the Rust
  heuristics, so frames are comparable.
- Frames go straight from the render texture into an `AVAssetWriterInputPixelBufferAdaptor`
  (HEVC, or H.264 for compatibility) in a temporary `.mov`. Playback frame rate is a setting,
  default 30 fps.
- **Scrubbing while running:** finished pairs are also shown as a live preview (latest
  quiver frame in the progress view), so long runs aren't a black box.

### 3.5 Public API sketch

```swift
public struct AnalysisRequest: Sendable {
    public var source: URL
    public var captureRate: FrameRate          // UI prefills from metadata
    public var frameRange: Range<Int>?
    public var stride: Int, pairStep: Int
    public var roi: CGRect?
    public var channel: Channel                // .luma, .green
    public var background: BackgroundSpec?     // .min(40) default
    public var preprocess: PreprocessConfig    // same defaults as Rust
    public var piv: PIVConfig                  // windows [96, 64], overlap 0.5, final 2, mask, validation
    public var scale: ScaleSpec                // pxPerMM or fovDegrees + axis + sheetDistance
    public var temporalSmoothing: TemporalSmoothing?   // D5
    public var render: RenderOptions?          // nil = fields only
}

public actor PIVSession {
    public init(device: MTLDevice? = nil) throws
    public static func probe(_ url: URL) async throws -> MediaInfo   // size, frames, container + capture rate and source
    public func analyze(_ request: AnalysisRequest) -> AsyncThrowingStream<AnalysisEvent, Error>
}
```

Config defaults are taken from the Rust structs: `PreprocessConfig` σ 1.0 and
normalize-radius 4 with ε 0.02; the CLI defaults `min_mean` 0.04 and `min_std` 0.015; PPR
1.3, median threshold 2 and ε 0.1. The two ports use the same parameter names, so a run's
settings read the same in both.

## 4. Mac app (`PIV.app`)

SwiftUI, macOS 15+, one window with three states: **Setup → Running → Result**.

**Setup**
- Import with **Open…** (⌘O) or by dragging a clip onto the window. The app shows the probe
  result: resolution, frame count, container rate, and the capture rate with its source
  ("Sony metadata: 1000 fps" or "container — check this"). This is the same capture-rate
  warning the Rust tool gives.
- Preview: a frame scrubber over the clip. **ROI** is drawn as a rectangle on the preview
  (with numeric fields), and the start/end of the frame range is set from the scrubber.
- **Timing:** capture frame rate (editable, prefilled; accepts `240000/1001` and `239.76`),
  stride, pair step. Shows the resulting dt and the number of pairs.
- **Scale:** none / px per mm / FOV + distance, with FOV in degrees, an axis picker
  (diagonal, horizontal, vertical) and camera-to-sheet distance in mm. Sheet thickness and
  density are optional (for KE units). The resolved mm/px appears live.
- **Advanced** (collapsed): windows, overlap, final iterations, background mode and N,
  smoothing σ, normalize radius, mask thresholds, validation thresholds, temporal smoothing.
- Settings are remembered per clip (keyed by file bookmark) and can be reset to defaults.

**Running**
- Analysis runs in a `Task` that consumes the `PIVSession` stream. The UI state is an
  `@Observable @MainActor` model updated from the events. Shown: a stage label (background /
  analysing / encoding), a determinate progress bar with pairs done of total, pairs per second,
  ETA, the latest quiver frame, and **Cancel**.

**Result**
- `AVPlayerView` (via `NSViewRepresentable`) playing the quiver movie with standard controls,
  plus frame stepping.
- Under the player: a Swift Charts panel of signed mean vorticity and total KE over the run,
  with a cursor following playback time; clicking the chart seeks. The current pair's
  readout (ω, |ω|, KE, coverage, t) is overlaid on the video (D4).
- Run summary as in `piv analyze`: valid/replaced/no-signal fractions, displacement
  percentiles with a stride hint, and noise floors.
- **Export movie…** saves the `.mov`. **Back to setup** keeps the settings, for the change →
  run → look loop.

Sandboxed, with user-selected read/write file access. No network.

## 5. Build and tooling

- **Package:** `swift/Package.swift`, swift-tools 6.0, platforms `.macOS(.v15)`, products
  `PIVKit` (library) and `pivkit-cli` (D3). Kernels ship as `.metal` resources compiled at
  runtime with `makeLibrary(source:)`, which works under plain `swift build` and `swift test`.
  For the app, a prebuilt `.metallib` would avoid the ~100 ms first-run compile. If that
  matters I'll add a build step later.
- **App project:** a checked-in `swift/App/PIV.xcodeproj` that uses Xcode 16+
  folder-synchronized groups (a small `project.pbxproj`, no file lists to maintain) and depends
  on `PIVKit` as a local package. It builds from the command line with
  `xcodebuild -project swift/App/PIV.xcodeproj -scheme PIV build`. No XcodeGen or Tuist is
  needed; neither is installed.
- **Tests:** `swift test` from `swift/`. GPU tests run on the local Mac, which is fine since
  there's no CI yet. The parity tests on real clips are skipped unless `PIV_CLIPS` points at
  `clips/`, like the `--include-ignored` Rust tests.

## 6. Verification

### 6.1 Parity with Rust (the main bar)

- **Fixtures from Rust.** A small Rust test-support binary (`rust/crates/piv-core/examples/fixtures.rs`)
  writes `swift/Tests/PIVKitTests/Fixtures/*.bin` with a short header: synthetic pairs from
  `piv-core::synthetic` (uniform shifts, rotation, shear, fog texture with noise, blank half),
  each with the prepared images, the per-pass raw peaks, and the validated final field. Swift
  tests load these and compare **stage by stage**, so a mismatch is pinned to preprocess,
  correlation, peak or validation.
- **Tolerances:** preprocessing to ~1e-5 (f32 on both). Raw peaks: |Δd| < 0.01 px on ≥ 99 % of
  windows, with identical integer peak locations. Flags identical on ≥ 99 %, where the
  differences may only be vectors whose PPR or median residual is within 1 % of a threshold.
  Final field RMS |Δd| < 0.02 px.
- **Unit tests ported from Rust**, for the same behaviour: `Grid`, `FrameRate` parsing,
  `find_peak` (broad peak + ripple, PPR = 4), isolated-particle sub-pixel accuracy (< 1e-3 px),
  flat window → no peak, validation (injected outliers, LOW_PPR, out-of-range), flowstats
  analytic fields, scale (C0141 estimate 0.2452 mm/px), and the Sony capture-rate probe on the
  existing header fixture.
- **Real clip.** `pivkit-cli analyze clips/C0141.MP4 --start-s 0.2 --end-s 1.2 --stride 5
  -o out/p3_c0141_swift/` writes `.npy` fields. `rust/scripts/compare_swift.py` (numpy + h5py)
  compares them with `piv analyze` on the same range: median |Δd|, flag agreement, and
  vorticity/KE series difference. The decoders differ (AVFoundation vs ffmpeg), so I'll first
  check that the decoded luma of a few frames matches (expect at most ±1 DN from deblocking or
  rounding differences) before blaming the correlator.

### 6.2 Performance

The Rust baseline on this machine class: 15 ms per 1080p pair at 96 → 64, 5.8 ms per frame
prepare, 68 pairs/s end to end (58 with video). **Target for PIVKit: ≥ 200 pairs/s for fields
only and ≥ 120 with the quiver movie on the M5 Max**, measured with `pivkit-cli bench`
(per-stage GPU times from command-buffer timestamps). These are targets, not promises. If
decoding turns out to be the limit, I'll report that rather than tune around it.
