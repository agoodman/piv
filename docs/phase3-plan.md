# Phase 3 plan: Swift + Metal PIV library and Mac app

## 1. Context

The Rust tool (`piv` CLI: info / analyze / smooth) works well, but every change means a CLI
run and a video to open. Phase 3 adds a native path for faster iteration:

1. **Repository split.** Move the Cargo workspace into `rust/`, so the Rust and Swift code
   can be built, tested and versioned separately.
2. **`PIVKit`**, a Swift package that does the same per-pair analysis as `piv-core`, with the
   heavy work (preprocessing, FFT cross-correlation, peak finding) in Metal compute kernels.
3. **`PIV.app`**, a SwiftUI Mac app built on `PIVKit`. You import a clip, set the capture
   frame rate, FOV, camera-to-sheet distance and the analysis parameters, run the analysis off
   the main thread with a progress indicator, then play the quiver result.

The Rust code stays the reference implementation. The Swift port is judged by how closely it
matches Rust on the same input (§6), not only by synthetic tests. HDF5 export from Swift is
deferred (D6).

### 3.1 Decoding (AVFoundation)

- `AVAssetReader` with `AVAssetReaderTrackOutput` asking for
  `kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange` (the 10-bit variant for >8-bit sources). The
  Y plane is the luma we analyse, so there's no RGB conversion, the same as Rust's `gray`.
- **Range parity:** ffmpeg's `gray` output expands video-range luma (16–235) to full range.
  The upload kernel does the same, (Y − 16) / 219 clamped to 0–1, so intensity thresholds like
  `min_mean 0.04` mean the same thing in both ports. Full-range sources are passed through
  unchanged. `channel green` maps to requesting BGRA and taking G.
- Planes come in as `CVPixelBuffer`s and go to Metal through `CVMetalTextureCache` without a
  copy. The upload kernel crops the ROI and writes a dense `float` buffer, the same layout as
  Rust's `Frame`.
- Frame indexing: a start time is converted to a frame index with the container rate, as in
  Rust. Frames are counted from the reader start and checked against presentation timestamps.
  The 40 background samples spread across the clip use one short `timeRange` read each.
- All five sample clips are 8-bit H.264 4:2:0 (checked with ffprobe), which AVFoundation
  decodes in hardware.

### 3.2 Correlation on the GPU

A pass correlates every window of the grid at once (1080p at 64 px / 50 %: 59 × 32 = 1 888
windows; at 96 px, 819). The default `[96, 64]` with two final iterations runs one 96 px pass
and two 64 px passes, so **about 82 % of the correlations are 64 × 64**.

#### Threadgroup memory: can a whole window live in a 64 × 64 tile?

The M5 Max reports `maxThreadgroupMemoryLength` = **32 768 bytes** (queried on this machine).
One 64 × 64 complex `float` plane is 64 · 64 · 8 = 32 768 bytes, **exactly the limit**:

- The two real windows fit in one plane by packing them as A + iB. After the forward
  transform the two spectra are separated using conjugate symmetry, so one plane is enough.
- That leaves **0 bytes** for anything else in threadgroup memory: the window mean/energy
  reductions, the signal-mask statistics, and the peak search. All of these would have to work
  with SIMD-group operations (`simd_sum`, `simd_max`, `simd_shuffle`) and registers, or reuse
  the plane memory when it isn't holding data (reductions before the plane is filled, the peak
  search on the real correlation plane after the inverse transform, which needs only 16 KB).
- The row transforms can stay in registers: a SIMD group of 32 threads holds a 64-point row
  (2 points per thread) and does the butterflies with `simd_shuffle_xor`. Only the transpose
  to columns goes through threadgroup memory.
- **Cost:** a threadgroup using all 32 KB limits each GPU core to few resident threadgroups
  (Apple doesn't publish the per-core total), which leaves less latency hiding. Whether a
  fused kernel beats the batched one has to be measured.
- `half` precision would halve the plane to 16 KB, but its ~3 significant digits are too few
  for the log-based 3-point sub-pixel fit. Not proposed.

**96 × 96 doesn't fit** (72 KB packed). Cutting a 96 px window into 64 px tiles doesn't give
the same correlation: summing sub-tile correlation planes is a different estimator, with
different edge loss and wrap-around. Changing the default first pass to 64 px would break
parity with Rust, and it would halve the largest measurable displacement (48 → 32 px). The
default was chosen on fog footage, so changing it is a separate question for later.

**Plan: two kernel paths, picked by window size.**

1. **Fused 64 × 64 kernel** (also used for 32 and 48), one threadgroup per window. It does the
   load (bilinear) → mean/energy/mask stats → packed forward FFT → conj(A)·B → inverse FFT →
   peak, PPR and sub-pixel fit in a single dispatch with no device-memory round trips. Window
   sizes ≤ 64 of the form 2ᵃ·3ᵇ are supported.
2. **Batched kernels** for larger windows (96, and up to 128). A load kernel writes packed
   windows to device memory, then batched 1-D FFT kernels run over all rows of all windows and
   then all columns. Each 1-D transform is ≤ 128 points and < 1 KB, in threadgroup memory,
   with radix-2 and radix-3 stages. A peak kernel finishes as in path 1.

Both paths share the same loader, FFT butterflies and peak code (Metal functions included from
one header), so they can't drift. A parity test runs 64 px windows through both paths and
requires them to agree to float rounding.

**Spike at the start of milestone 3:**

- **MPSGraph FFT:** batched 819 × 96² and 1 888 × 64², timed against the custom batched
  kernel.
- **Fused 64 × 64:** timed against the batched path on 1 888 × 64². If the fused kernel isn't
  faster, it is dropped and everything uses the batched path. This is less code, with the same
  results.

I'll report the timings before going further. Window sizes neither path handles (for example
80 = 2⁴·5) are rejected in config validation with a clear message.

Common to both paths:

- **Origins:** the `place` logic from `multipass.rs` (symmetric split, clamped at borders) runs
  on the CPU and passes fractional origins in a buffer.
- **Bilinear interpolation:** done by hand in `float`, not with the texture sampler, because
  the sampler's 8-bit fractional weights would bias the sub-pixel results.
- **Scaling:** by 1/(n²·√(Ea·Eb)), as in Rust.
- **Output per window:** `dx, dy, ppr, flag`.

### 3.3 Pipeline and concurrency

```
FrameReader (AsyncSequence of CVPixelBuffer, own task)
  → upload + preprocess (Metal)  → PreparedFrame ring (stride + 1 GPU buffers, recycled)
  → per pair: for each pass { CPU place origins → GPU correlate → CPU validate }
  → PairResult (VectorField + summary + FlowStats)
  → QuiverRenderer → AVAssetWriter
  → after the last pair: optional temporal smoothing → smoothed fields + stats
```

- `PIVSession` is an **actor** that owns the Metal device, pipelines and buffer pools. The
  public API is `func analyze(_ request: AnalysisRequest) -> AsyncThrowingStream<AnalysisEvent, Error>`.
  Events are `.progress(pairsDone, pairsTotal, stage)`, `.pair(PairResult)` and
  `.finished(RunResult)`. Cancelling the consuming task stops decoding and GPU submission and
  deletes the partial movie.
- Two or three pairs are in flight at a time (command-buffer completion handlers resume
  continuations), so CPU validation for pair *k* overlaps GPU correlation of pair *k + 1*.
- Swift 6 language mode with strict concurrency. Metal objects stay inside the actor, and only
  `Sendable` value types (fields as `[Float]` plus `Grid`) cross out of it.
- The background estimate (min of N frames across the clip) is a first stage with its own
  progress.
- **Temporal smoothing (D5)** needs neighbouring pairs, so it runs after the last pair. Raw
  fields are kept in memory (≈ 1 888 vectors × 4 arrays per pair, about 30 KB, so even
  3 700 pairs is ~110 MB). With smoothing on, the quiver movie is rendered from the smoothed
  fields in a second render pass that re-decodes the clip, which `piv smooth --video` also
  does. The extra stage shows in the progress.

### 3.4 Quiver video

- `QuiverRenderer` draws on the GPU. The background is the frame with the same auto gain as
  `QuiverStyle::auto` (99th percentile from a sparse sample). Arrows (shaft and head,
  antialiased) are drawn instanced, coloured by magnitude with the same colour map, and
  magenta for replaced vectors. Arrow scale and colour range are fixed from the first pairs,
  using the same heuristics as Rust, so frames can be compared.
- Frames go straight from the render texture into an `AVAssetWriterInputPixelBufferAdaptor`
  (HEVC, or H.264 for compatibility) in a temporary `.mov`. Playback frame rate is a setting,
  default 30 fps.
- **Scrubbing while running:** finished pairs are also shown as a live preview (the latest
  quiver frame in the progress view), so long runs aren't a black box.

### 3.5 Field output for comparison

Without HDF5 (D6), the app keeps fields in memory and saves only the movie. `pivkit analyze`
can still write the fields for the parity check against Rust, as a directory of plain `.npy`
files (a header plus raw little-endian arrays, written in a few lines of Swift with no C
dependency):

- `dx.npy, dy.npy, u.npy, v.npy, peak_ratio.npy, flags.npy` as `[pairs, ny, nx]`.
- `grid_x.npy, grid_y.npy`, `frame_a.npy, frame_b.npy, t.npy`, and `stats_*.npy` for the
  flow series.
- `run.json`, using the same keys as the Rust `run_json`, plus
  `"implementation": "pivkit <version>"`.
- With smoothing on, the smoothed fields and `support.npy` go at the top level and the raw
  fields under `raw/`, mirroring the `piv smooth` HDF5 layout. Adding HDF5 export later is
  then a change of container, not of layout.

### 3.6 Public API sketch

```swift
public struct AnalysisRequest: Sendable {
    public var source: URL
    public var captureRate: FrameRate          // UI prefills from metadata
    public var frameRange: Range<Int>?
    public var stride: Int, pairStep: Int
    public var roi: CGRect?
    public var channel: Channel                // .luma, .green
    public var background: BackgroundSpec?     // .min(40) default
    public var preprocess: PreprocessConfig    // same defaults as Rust
    public var piv: PIVConfig                  // windows [96, 64], overlap 0.5, final 2, mask, validation
    public var scale: ScaleSpec                // pxPerMM or fovDegrees + axis + sheetDistance
    public var flow: FlowOptions               // density, sheet thickness (KE units)
    public var temporalSmoothing: TemporalSmoothing?   // nil = off; window N, mean/median, min support
    public var render: RenderOptions?          // nil = fields only
}

public actor PIVSession {
    public init(device: MTLDevice? = nil) throws
    public static func probe(_ url: URL) async throws -> MediaInfo   // size, frames, container + capture rate and source
    public func analyze(_ request: AnalysisRequest) -> AsyncThrowingStream<AnalysisEvent, Error>
}

public struct RunResult: Sendable { /* grid, pairs, raw (+ smoothed) fields, flow series, summary, movie URL */ }
```

Config defaults are taken from the Rust structs: `PreprocessConfig` σ 1.0 and
normalize-radius 4 with ε 0.02; the CLI defaults `min_mean` 0.04 and `min_std` 0.015; PPR
1.3, median threshold 2 and ε 0.1; and temporal smoothing at 9 pairs with the median kernel
when turned on. The two ports use the same parameter names, so a run's settings read the same
in both.

## 4. Mac app (`PIV.app`)

SwiftUI, macOS 15+, one window with three states: **Setup → Running → Result**.

**Setup**
- Import with **Open…** (⌘O) or by dragging a clip onto the window. The app shows the probe
  result: resolution, frame count, container rate, and the capture rate with its source
  ("Sony metadata: 1000 fps" or "container — check this"). This is the same capture-rate
  warning the Rust tool gives.
- Preview: a frame scrubber over the clip. **ROI** is drawn as a rectangle on the preview
  (with numeric fields), and the start/end of the frame range is set from the scrubber.
- **Timing:** capture frame rate (editable, prefilled; accepts `240000/1001` and `239.76`),
  stride, pair step. Shows the resulting dt and the number of pairs.
- **Scale:** none / px per mm / FOV + distance, with FOV in degrees, an axis picker
  (diagonal, horizontal, vertical) and camera-to-sheet distance in mm. Sheet thickness and
  density are optional (for KE units). The resolved mm/px appears live.
- **Temporal smoothing toggle** (D5), off by default. When on, it shows the window (odd N,
  default 9, with its duration in ms at the current stride and frame rate) and the
  mean/median kernel.
- **Advanced** (collapsed): windows, overlap, final iterations, background mode and N,
  smoothing σ, normalize radius, mask thresholds, validation thresholds, min support.
- Settings are remembered per clip (keyed by file bookmark) and can be reset to defaults.

**Running**
- Analysis runs in a `Task` that consumes the `PIVSession` stream. The UI state is an
  `@Observable @MainActor` model updated from the events. Shown: a stage label (background /
  analysing / smoothing / encoding), a determinate progress bar with pairs done of total,
  pairs per second, ETA, the latest quiver frame, and **Cancel**.

**Result**
- `AVPlayerView` (via `NSViewRepresentable`) playing the quiver movie with standard controls,
  plus frame stepping.
- **Live readouts (D4)** over the video: the current pair's signed ω, |ω|, KE (in the most
  physical units the run supports), coverage, and t. They are SwiftUI views that follow
  playback time, not burned into the movie.
- Under the player: a Swift Charts panel of signed mean vorticity and total KE over the run,
  with a cursor following playback; clicking the chart seeks. With smoothing on, smoothed is
  drawn bright and raw dim, as in `piv smooth --video`.
- Run summary as in `piv analyze`: valid/replaced/no-signal fractions, displacement
  percentiles with a stride hint, and noise floors.
- **Export movie…** saves the quiver `.mov`. Fields aren't saved from the app in phase 3 (D6);
  use `pivkit analyze` for field output.
- **Back to setup** keeps the settings, for the change → run → look loop.

Sandboxed, with user-selected read/write file access. No network.

## 5. Build and tooling

- **Package:** root `Package.swift`, swift-tools 6.0, platforms `.macOS(.v15)`. Products:
  - `PIVKit`: library, no C dependencies.
  - `pivkit`: executable (D3), with `info`, `analyze` (writes `.npy` fields and optionally a
    `.mov`) and `bench`.

  Kernels ship as `.metal` resources compiled at runtime with `makeLibrary(source:)`, which
  works under plain `swift build` and `swift test`. For the app, a prebuilt `.metallib` would
  avoid the ~100 ms first-run compile, and I'll add that build step if it matters.
- **App project:** a checked-in `swift/App/PIV.xcodeproj` (D2) that uses Xcode 16+
  folder-synchronized groups (a small `project.pbxproj` with no file lists to maintain). It
  depends on the root package as a local package (`../..`). It builds from the command line with
  `xcodebuild -project swift/App/PIV.xcodeproj -scheme PIV build`. No XcodeGen or Tuist is
  needed; neither is installed.
- **Tests:** `swift test` from the repo root. GPU tests run on the local Mac, which is fine
  since there's no CI yet. The parity tests on real clips are skipped unless `PIV_CLIPS`
  points at `clips/`, like the `--include-ignored` Rust tests.

## 6. Verification

### 6.1 Parity with Rust (the main bar)

- **Fixtures from Rust.** A small Rust example (`rust/crates/piv-core/examples/fixtures.rs`)
  writes `swift/Tests/PIVKitTests/Fixtures/*.bin` with a short header. They hold synthetic
  pairs from `piv-core::synthetic` (uniform shifts, rotation, shear, fog texture with noise,
  blank half), each with the prepared images, the per-pass raw peaks, and the validated final
  field. Swift tests load these and compare **stage by stage**, so a mismatch is pinned to
  preprocess, correlation, peak or validation. Window sizes 32, 64 and 96 cover both kernel
  paths.
- **Tolerances:** preprocessing to ~1e-5 (f32 on both). Raw peaks: |Δd| < 0.01 px on ≥ 99 % of
  windows, with identical integer peak locations. Flags identical on ≥ 99 %, where the
  differences may only be vectors whose PPR or median residual is within 1 % of a threshold.
  Final field RMS |Δd| < 0.02 px. Temporal smoothing is checked against `piv smooth` output
  on the same raw fields to 1e-5.
- **Unit tests ported from Rust**, for the same behaviour: `Grid`, `FrameRate` parsing,
  `find_peak` (broad peak + ripple, PPR = 4), isolated-particle sub-pixel accuracy (< 1e-3 px),
  flat window → no peak, validation (injected outliers, LOW_PPR, out-of-range), flowstats
  analytic fields, scale (C0141 estimate 0.2452 mm/px), temporal smoothing, and the Sony
  capture-rate probe on the existing header fixture.
- **Real clip.** `pivkit analyze clips/C0141.MP4 --start-s 0.2 --end-s 1.2 --stride 5
  -o out/p3_c0141_swift/` writes `.npy` fields, and `piv analyze` writes HDF5 with the same
  range and options. `rust/scripts/compare_runs.py` (numpy + h5py) reports median |Δd|, flag agreement, and the
  vorticity/KE series difference. The decoders differ (AVFoundation vs ffmpeg), so I'll first
  check that the decoded luma of a few frames matches (expect at most ±1 DN from rounding)
  before blaming the correlator.

### 6.2 Performance

The Rust baseline on this machine class: 15 ms per 1080p pair at 96 → 64, 5.8 ms per frame
prepare, 68 pairs/s end to end (58 with video). **Target for PIVKit: ≥ 200 pairs/s for fields
only and ≥ 120 with the quiver movie on the M5 Max**, measured with `pivkit bench` (per-stage
GPU times from command-buffer timestamps). These are targets, not promises. If decoding turns
out to be the limit, I'll report that rather than tune around it.

## 10. Milestone 3 findings (2026-10-29)

### Parity with Rust

The GPU correlation matches `piv-core` to **f32 rounding**: on every pass of all seven
reference cases (particles, rotation, shear at 48/24 px, a 20 px shift, fog with the default
96 → 64 windows and preprocessing, background + mask, blank half), the worst raw-peak
difference is **3e-6 px**, peak ratios agree to 7e-7 (relative), and NO_SIGNAL decisions and
final flags are **identical**. Final-field RMS differences are 2e-7 to 1e-6 px. The CPU stages
(window placement, validation) match Rust bit for bit. The tests now require 1e-4 px rather
than the planned 0.01 px, so any regression shows.

### Kernel timings (M5 Max, 1920×1080, 50 % overlap; GPU time per pass, median)

| Window (windows per pass) | Fused (threadgroup memory) | Batched (custom FFT) | Hybrid (MPSGraph FFT) |
|---|---|---|---|
| 96 px (819) | — (doesn't fit) | 2.95 ms | **2.52 ms** |
| 64 px (1 888) | 3.42 ms | 2.70 ms | **1.70 ms** |
| 48 px (3 404) | — (not a power of two) | **2.98 ms** | 3.38 ms |
| 32 px (7 854) | **1.62 ms** | 2.90 ms | 1.95 ms |

Breakdown of the batched path at 64 px: load 0.34, forward FFT 0.97, cross spectrum 0.19,
inverse FFT 0.97, peak 0.13 ms. **The FFT is ~75 % of the time** and costs about the same at
every window size (~1 ms per direction), so it is limited by memory traffic, not arithmetic.
Two attempts to speed up the custom FFT didn't help: moving the twiddle table out of `constant`
memory made no difference, and re-mapping loads/stores for coalesced column access made it
~35 % *slower* (reverted).

- **The fused 64 × 64 kernel is slower than batched** (3.42 vs 2.70 ms), as the occupancy
  concern in §3.2 predicted: a 32 KB threadgroup leaves each GPU core very few windows in
  flight. At 32 px (an 8 KB plane) the fused kernel is the fastest option. `auto` now uses
  fused only for windows ≤ 32 px.
- **MPSGraph's FFT is faster than mine at 64 and 96 px** (and at 32), slower at 48. Wrapped
  around my load / cross-spectrum / peak kernels in one command buffer ("hybrid"), it gives
  the same peaks as the custom path to 7e-7 px.

### Per pair (default 96 → 64 → 64)

| | GPU time per pair | Pairs/s if the GPU is kept busy |
|---|---|---|
| Batched (current default) | 8.4 ms | ~120 |
| Fused 64 | 9.8 ms | ~100 |
| Hybrid (MPSGraph FFT at 64/96) | 5.9 ms | ~170 |
| Hybrid + packing two inverse transforms into one (estimate) | ~5.0 ms | ~200 |

Measured wall time today is **10.5 ms per pair (95 pairs/s, 1.4× Rust's 68)**, because the
three passes run back to back with CPU validation in between and nothing overlaps.
Pipelining pairs (milestones 4–5) should bring wall time close to the GPU time. The
≥ 200 pairs/s target needs the hybrid FFT plus the inverse-packing trick: the cross spectrum
of a real pair is Hermitian, so two windows' inverse transforms can share one complex FFT.

### Decision and result (2026-10-29)

Adopted the MPSGraph FFT for windows ≥ 64 px (`auto`), with the custom batched FFT for 48 px
and the fused kernel for ≤ 32 px. Both batched paths now pack two windows' cross spectra into
one inverse transform. Measured per pass: 96 px 2.02 ms, 64 px 1.45 ms (MPSGraph); 48 px
2.48 ms (custom); 32 px 1.62 ms (fused). **Default pair: 4.9 ms of GPU time (~200 pairs/s
when pipelined); 8.7 ms wall unpipelined (115 pairs/s).** Parity is unchanged: ≤ 2e-6 px,
identical flags, on all three paths.

## 11. Milestone 4 findings (2026-10-29)

### The Rust tool's `luma` is not the Y plane

AVFoundation's decoded Y plane is **bit-identical** to FFmpeg's (`extractplanes=y`) on C0141.
But `piv --channel luma` (FFmpeg `-pix_fmt gray`) does not deliver that plane. FFmpeg's
gray conversion of these BT.709 limited-range files mixes in chroma: for a given Y the gray
value spreads over several DN, and on C0141 frame 0 the mean is 23.3 DN against Y's 37.2
(about 37 % darker). The Rust docs describe `luma` as "the decoded Y plane: no colour
conversion", so the current behaviour doesn't match its documentation.

- PIVKit reads the stored Y plane (`Channel.luma`).
- `piv` gains `--channel yplane` (FFmpeg `extractplanes=y`, taken before any ROI crop), so
  the two can be compared. **`luma` is unchanged**, so existing runs and the phase 1–2
  thresholds (`--min-mean 0.04 --min-std 0.015`, tuned on the darker conversion) still mean
  what they did.
- **Open question:** should Rust's default become `yplane`? The mask thresholds would then
  apply to brighter values: about 1.6× on average, varying with colour.

### Frame indexing after a seek

AVAssetReader also emits a sample that only *overlaps* the start of the requested time
range, with its timestamp clipped to the range start. Starting the read half a frame early
(as the Rust tool does with FFmpeg) therefore produced frame k − 1's picture labelled k, and
every pair was off by one frame. The reader now starts at the frame's exact rational
timestamp and never repeats an index. A clip test checks seeked against sequential decoding.

### Parity on a real clip (C0141, 1 s from 0.2 s, stride 5, defaults; Rust `--channel yplane`)

| | Rust | Swift |
|---|---|---|
| Valid / rejected / no signal | 47.4 / 37.6 / 15.0 % | 47.4 / 37.6 / 15.0 % |
| Flags identical | — | 1 878 552 of 1 878 560 (8 differ) |
| \|Δd\| where both accept | — | median 5e-7 px, p99 1.2e-5 px, max 0.06 px |
| Mean vorticity / mean KE per pair | — | median relative difference 6e-7 / 1e-7 |

The single 0.06 px outlier sits next to a vector whose flag flipped, so its replacement median
changed. Preprocessing on the GPU stays within 3.5e-5 of Rust's prepared images. Local
normalization uses separable box sums in f32 (var = E[v²] − mean²) rather than Rust's f64
integral image; that is 6× faster, at a cost of 2e-5 to 3e-5 precision.

### Throughput

| Run | Pairs/s |
|---|---|
| Swift, C0141 1 s (995 pairs) | 117–129 |
| Swift, **full C0141 (3 715 pairs) + temporal 9**, 33.5 s end to end | **132** |
| Rust, same machine today (`main` build, same range) | 17–19 |

Swift is ~7× faster than Rust on this machine today. Both are slower than when phase 1
measured Rust at 68 pairs/s: a `main` build shows the same drop, so the cause isn't phase 3,
and Low Power Mode is off. Swift falls short of the ≥ 200 pairs/s target. With frames
already on the GPU and 3–6 pairs in flight, it tops out at ~130–145 pairs/s (7–7.7 ms per
pair), against 4.9 ms of measured GPU time per pair. Per-pass CPU encoding is ≤ 0.6 ms, and
decoding isn't the limit (0.2 s of waiting per 1 000 frames). The remaining gap is
structural: every pass waits for the CPU to validate and place the next windows, so GPU work
arrives in bursts and wall timings vary run to run (the same unpipelined pair measured
9.9–19 ms). Moving validation and window placement onto the GPU would put a whole pair in one
command buffer. That is the next lever if more speed is wanted.

### Decisions from review (2026-10-29)

- **Rust keeps `luma` (FFmpeg's gray conversion) as its default**; `--channel yplane` stays
  available, and Swift/Rust comparisons use it.
- **Validation and window placement moved to the GPU** (below).

### Validation on the GPU

Window placement (predictor sampling, symmetric split), pair assembly, the per-vector tests,
the normalized median test and replacement now run as Metal kernels. All passes of a pair are
encoded into one command buffer, and the CPU reads back only the final field. The kernels
repeat Rust's f32 operations in order, with fused multiply-add contraction disabled
(`#pragma METAL fp contract(off)`). Given Rust's inputs, placement and validation reproduce
Rust **bit for bit** on every pass of every reference case. Frame preparation no longer waits
for the GPU either: it commits and returns, since later work on the same queue runs after it.

| | Before | After |
|---|---|---|
| One pair, unpipelined (synthetic 1080p) | 8.7–19 ms (noisy) | **6.0 ms** (steady) |
| C0141 1 s (995 pairs) | 117–129 pairs/s | **161–171 pairs/s** |
| Full C0141 (3 715 pairs) + temporal 9 | 132 pairs/s | **177 pairs/s** (20.9 s) |

The run is now GPU-bound: the loop's waiting is almost all on pair results. Parity on C0141
is unchanged (10 of 1.88 M flags differ; median |Δd| 5e-7 px). The remaining distance to
200 pairs/s is kernel time: ~4.9 ms of correlation plus ~1 ms of preparation per pair.

## 12. Milestone 5 findings (2026-10-29)

### Built

- **`QuiverRenderer`** (Metal): a full-screen pass draws the frame in gray (Rust's
  `min(raw·gain, 1)·180`), then one instanced draw places every arrow. Arrow geometry is built
  in the vertex shader (shaft plus ±24° head strokes, as in Rust) and antialiased by distance
  to the stroke. It uses the same colour map, magenta for replaced vectors, and the same
  automatic style from the first pair (`QuiverStyle.auto`).
- **`MovieWriter`** (AVAssetWriter, H.264 or HEVC, ~0.25 bit/pixel, padded to even sizes).
  `renderQuiverMovie` re-decodes frame A of every pair and draws the fields the run is about
  (smoothed when smoothing is on, D9) straight into the writer's pixel buffers.
- **`PIVSession`** (actor): `analyze(request, render:)` returns an `AsyncThrowingStream` of
  `.progress`, `.preview` (a quiver image at most twice a second during analysis),
  `.analysed(result)` and `.finished(result, movie:)`. Dropping the stream or cancelling its
  consumer cancels the run; a partial movie is deleted.
- **`pivkit analyze --video`** writes `<output>_quiver.mov`.

| C0141, 1 s (995 pairs) | Time | Rate |
|---|---|---|
| Analysis (defaults) | 4.4 s | 227 pairs/s |
| Movie render + encode | 2.3 s | 432 frames/s |
| Movie size (33 s at 30 fps) | 64 MB | Rust's x264 CRF 18: ~22 Mbit/s, ours ~15 |

### Mask defaults for the Y plane

With the Rust tool's thresholds (`--min-mean 0.04 --min-std 0.015`), the brighter Y plane
leaves only 15 % of C0141's windows masked as no signal, against **62.6 %** for `piv
analyze` on its `luma` conversion. The difference shows up as vectors over the unseeded
background. Scaling both thresholds by the brightness ratio (×1.6 → **0.064 / 0.024**) gives
**63.2 %** no signal, a match. It also leaves more valid vectors than Rust `luma` (22.8 vs
16.3 %) and fewer rejected (13.9 vs 21.1 %). These are now PIVKit's defaults
(`AnalysisRequest.defaultMask`); Rust is unchanged.

### Bug found and fixed: decoder crash on cancel

Three intermittent segfaults (crash reports in `~/Library/Logs/DiagnosticReports`) were
inside `AVAssetReaderOutput.copyNextSampleBuffer`. `cancel()` called `cancelReading()` from
another thread while the decoding thread was reading. Only the decoding thread touches the
reader now; `cancel()` sets a flag. A stress loop (12 runs, 132 decoder cancellations)
produced no new crashes.

## 13. Milestone 6: the Mac app (2026-10-29)

`swift/App/PIV.xcodeproj` (synchronized folders, local package `../..`, sandboxed with
user-selected file access, ad-hoc signed for local runs). Build and test:

```sh
xcodebuild -project swift/App/PIV.xcodeproj -scheme PIV build
xcodebuild -project swift/App/PIV.xcodeproj -scheme PIV test
```

- **Setup:** open (⌘O) or drop a clip. A frame preview with a scrubber sets the start and
  end of the range, and dragging on the frame draws the ROI. The form covers capture rate
  (prefilled from metadata, with its source and a warning when only the container rate is
  known), stride, pair step and dt, then scale (none, px/mm, or FOV + axis + distance, with
  the resolved mm/px), the temporal smoothing toggle, and an Advanced section (windows,
  overlap, passes, background, preprocessing, mask, validation, movie fps). Settings are
  remembered per clip.
- **Running:** stage, progress, pairs/s, ETA, a live quiver preview (twice a second), Cancel.
- **Result:** the quiver movie in `AVPlayerView` (frame stepping). The readout overlay (t,
  pair, ω, |ω|, KE total and per mass, coverage) follows playback. Swift Charts shows mean
  vorticity and total KE with a cursor (click to seek; raw dim behind smoothed when smoothing
  is on), next to the run summary. Export Movie… copies the `.mov`.
- **Tests:** 8 app tests (state machine against a scripted fake service; settings →
  request mapping). They caught a bug where the capture-rate note disappeared when the rate
  matched the metadata. A DEBUG-only smoke hook (`PIV_SMOKE_CLIP`, `PIV_SMOKE_OUT`) runs the
  real app unattended on a clip in its container and saves snapshots, the first preview and
  the movie. That confirmed open → run → result, previews and a valid 145-frame movie in the
  sandbox.
- **Bug found and fixed in PIVKit:** a clip cut without re-encoding (edit list) has more
  samples (159) than presented frames (151). The frame count now uses the presented
  duration, so background sampling no longer asks for frames that are never decoded. Rust's
  ffprobe `nb_frames` has the same issue.

What the work turned up, beyond the plan:

1. **FFmpeg's `gray` is not the Y plane** on the sample clips (§11). Rust keeps `luma` as

2. **AVAssetReader clips overlapping samples** at a range start, which shifted pairs by
   one frame until fixed (§11).
3. **Edit lists** can leave more samples than presented frames, which affects any
   `nb_frames`-based frame count, including Rust's (§13).
4. **The 64 × 64 fused kernel** fits the 32 KB threadgroup limit but is slower than the
   batched path (occupancy); it wins only at 32 px (§10).
